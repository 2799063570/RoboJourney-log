# ROS1 TCPROS、UDP 与 ROS2 DDS 通信

> 本文用于建立通信机制的工作模型，不应把“TCP、UDP、DDS”理解为可一一替换的三种同层协议。ROS2 用户代码通过 `rclcpp/rcl` 与 `rmw` 接口使用中间件；具体 DDS 实现、发现方式与同机优化取决于所选 RMW、系统配置和部署环境。

## 先记住四个边界

- ROS1 常见 topic 传输是 TCPROS；Master 负责发现和连接信息匹配，建立连接后不转发普通 topic 数据。
- ROS2 通常使用 DDS/RTPS 类中间件，但不要假设所有实现都固定使用 UDP 组播、共享内存或零拷贝。
- QoS 的 `History` 决定缓存策略；晚加入者能否拿到历史数据还取决于 durability 等策略。
- 同进程组件在开启进程内通信后可避免部分复制；不同进程的共享内存与零拷贝属于实现相关优化，必须实测验证。

## 通信机制对比

就我个人而言，目前主要接触到的为TCP、UDP、以及ROS 2中新接触到的DDS

下面我们记录一下三者之间的差异

## TCP (传输控制协议)：严谨的“挂号信”

TCP 是互联网最常用的协议（比如你浏览网页），它的核心设计哲学是**绝对可靠**。

- **工作机制：** 经典的“三次握手”建立连接。TCP 使用确认、重传和有序字节流来提高可靠性；当网络长期异常时，连接也可能超时或失败，而不是无限重传。
- **在 ROS 1 中的应用 (`TCPROS`)：** 它是 ROS 1 的默认通信方式。当你发布一个话题时，底层实际上是建立了一条 TCP 连接。
- **致命弱点 (队头阻塞)：** 假设你在通过 TCP 传输高频的雷达或相机数据，如果中间因为网络抖动丢失了一个数据包，TCP 会暂停后续所有数据的交付，死等那个丢失的包重传。对于机器人来说，这意味着你的控制节点可能会突然卡顿几百毫秒，拿到的是“过期”的旧数据，这对实时控制是灾难性的。

TCP 的“三次握手”（Three-way Handshake）是计算机网络中最经典、也最精妙的设计之一。它的根本目的是在通信双方真正开始发送数据之前，**确保双方的收发能力都正常，并同步彼此的初始序列号，从而建立一条可靠的、全双工（双向同行）的通信通道。**

我们可以用日常打视频电话的逻辑来类比：

- **A：** “喂，能听到我说话吗？”（测试 A 的发送和 B 的接收）
- **B：** “我能听到！那你能听到我说话吗？”（确认 B 的接收和发送，以及 A 的发送没问题）
- **A：** “我也能听到！那我们开始聊吧。”（确认 A 的接收和 B 的发送没问题，正式建立连接）



## UDP (用户数据报协议)：极速的“广播电台”

UDP 的核心设计哲学是**天下武功，唯快不破**。

- **工作机制：** 没有任何握手，也不管对方收没收到，发送方只管以最快的速度把数据“扔”到网络上。这就导致数据包可能会丢失、重复或者乱序到达。
- **在 ROS 1 中的应用 (`UDPROS`)：** ROS 1 其实支持 UDP，但因为配置麻烦且缺乏高级管理，在实际工程中极少被正确使用。
- **优势与场景：** 因为没有重传的开销，它的延迟极低。非常适合传输视频流或者极高频率的传感器状态——因为丢了一两帧数据根本不影响大局，最新的数据永远比旧数据更有价值。


## DDS (数据分发服务)：智能的“现代化物流枢纽”

既然 TCP 太慢，UDP 又太不可靠，那现代机器人该用什么？答案就是 DDS。

DDS 是一个由 `OMG`（对象管理组织）制定的工业级分布式通信标准。**在 ROS 2 的底层实现中，DDS 主要使用的是基于 UDP 协议的 `RTPS`（实时发布订阅）协议。**

DDS 巧妙地结合了 UDP 的极速，并通过在应用层增加一层智能管理，弥补了 UDP 的缺陷。它的核心武器是 **`QoS` (Quality of Service，服务质量)**：

- **真正的以数据为中心 (`Data-Centric`)：** 在 TCP/UDP 中，你关注的是“发给哪个 IP 端口”。在 DDS 中，节点根本不关心 IP，它们只关心“全局数据空间（Global Data Space）”里的某个 Topic。
    
- **灵活的 `QoS` 策略：** DDS 允许开发者像点菜一样，为不同的数据配置不同的传输策略：
    
    - **Reliability (可靠性)：** 你可以选择 `Reliable`（像 TCP 一样保证送达，用于关键控制指令），或者选择 `Best Effort`（像 UDP 一样尽力而为，用于高频传感器数据）。
    - **History (历史记录)：** 控制发布端或订阅端保存多少条样本：`Keep Last` 保留最近 N 条，`Keep All` 尝试保留所有受资源限制的样本。晚加入者是否收到旧数据还需要结合 durability 设置。
    - **Deadline (截止时间)：** 设定某个节点必须在规定时间内收到数据，否则直接触发报警回调。这对于严格的实时系统至关重要。

我们分析一下这个过程

1. 首先是发现通信双方。发布者和订阅者启动后会利用 DDS discovery 自动发现彼此；默认配置常使用组播，但实际行为可由中间件、网络和 discovery 配置改变，因此不能把 UDP 组播当作唯一前提。
2. QoS 策略严格匹配。DDS 执行的是非常严格的**兼容性协商（Compatibility Check）**。它不会去自动修改你的配置来迎合对方，而是去对比双方的底线：
	- 如果发布者提供的是 `Reliable`（可靠传输），订阅者要求的是 `Best Effort`（尽力而为），这是兼容的（向下兼容），连接成功建立。
	- 如果发布者只是 `Best Effort`，而订阅者强硬要求 `Reliable`，**连接将直接失败**。DDS 不会报错崩溃，但数据就是通不了。这也是很多初学者在 ROS 2 中遇到“节点都在运行，话题也能 echo 出列表，但就是收不到数据”的头号原因。
3. 通信
	- **情况 A：同一个进程内 (Intra-process)** 。如果你把视觉节点和控制节点写成了代码级别的“组件（Component）”，并在同一个 C++ 宿主程序（通过单线程或多线程 Executor）里加载它们。这时候，ROS 2 确实会**直接传递 C++ 智能指针（`std::unique_ptr`）**，实现真正的“零拷贝（Zero-copy）”。不论你的点云图有多大，传输延迟几乎为零，因为内存根本没动。
	- **情况 B：同一台机器，但不同进程 (Inter-process)** 。不同进程不能直接传递彼此的普通指针。一些 DDS/RMW 实现可配置或自动选择共享内存等优化，但是否可用、复制次数和性能都依赖实现与部署，需用实际 profile 验证。
	- **情况 C: 不同机器**。  只要节点分布在两台或多台不同的物理机（或虚拟机、不同的 Docker 容器）上，只要处于同一局域网，底层的确是彻底抛弃了 TCP，直接使用 **UDP + RTPS 协议** 来完成高效且具备定制可靠性的数据收发。

目前本人写的程序基本上一个节点就是一个进程，但是在真正面向工业落地、对性能要求极高的场景中，**把多个节点塞进同一个进程，不仅不罕见，反而是必须要掌握的核心优化手段。**

- ROS 1 (如 Noetic) 中的妥协：Nodelet 机制

	在复杂的感知与规划管线中，跨进程通信的代价是非常昂贵的。 假设系统使用 RealSense D435i 深度相机，以 30Hz 的频率不断生成密集的 3D 点云。紧接着，这些海量数据需要送给下游的 YOLO11-OBB 深度学习模型去识别物体的旋转包围框，最后再交给 MoveIt 里的 RRT-Connect 等算法去做避障规划。

	如果这三个环节是独立的进程，那么每一帧庞大的点云和图像数据都要经历：**序列化 -> 操作系统底层的跨进程拷贝（走本地回环网络或 TCP） -> 反序列化**。这会瞬间拉高 CPU 占用率，并带来致命的延迟。
	
	为了解决这个问题，ROS 1 发明了 **Nodelet** 机制。它的思想就是启动一个单独的 `Nodelet Manager` 进程，然后把相机驱动、目标检测等功能写成动态链接库（插件）塞进这一个进程里。在这个单进程内，各个模块之间互传图像，底层就退化成了极其高效的 **C++ 指针传递（Zero-copy 零拷贝）**。 只不过，ROS 1 的 Nodelet 机制 API 设计得比较繁琐，配置文件写起来也很痛苦，导致很多开发者望而却步。

- ROS 2 的终极进化：Component (组件化开发)

	到了 ROS 2，组件化提供了“多节点同进程”的标准方式之一。
	
	组件通常将继承 `rclcpp::Node` 的节点类编译为共享库，由 Component Container 加载；普通节点仍然可以保留自己的 `main()`，组件化不是强制要求。
	
	- **运行方式：** 部署时，你只需要启动一个轻量级的 **Component Container（组件容器进程）**，然后通过命令行或 Launch 文件，把视觉识别组件、运动规划组件、Aubo i5 机械臂的硬件接口组件，像搭积木一样动态加载到这**唯一的一个进程**里。
	    
	- **降维打击：** 只要这些组件同处一个容器进程，当你开启了 `use_intra_process_comms` 标志，底层的 DDS 就会非常聪明地“退居幕后”。数据的传递彻底绕开了复杂的网络协议，直接变成了 `std::unique_ptr` 智能指针的快速转移。

## ROS 通信过程分析

以话题发布的过程为例，我们分析一下通信的过程

例如我们视觉检测节点检测到了分拣平台上的物体的旋转框，现在需要把抓取参数通过话题`/target_pose` 话题发布出去，交由下游控制`Aubo i5 `机械臂的规划节点（比如 MoveIt 节点）来订阅并执行抓取。

对于ROS 1，过程依赖于`roscore`即Master进行操控

1. **第 1 步：视觉节点“登记注册”**。YOLO 视觉节点启动后，首先必须通过 XML-RPC 协议找到 `roscore`（Master 节点）。它向 Master 报告：“我是一个发布者，我要发布 `/target_pose` 话题，我的数据通信端口是 4321。” Master 将这条信息记录在内部的注册表中。
2. **第 2 步：机械臂节点“挂号寻医”** 。机械臂的 MoveIt 控制节点启动，同样去问 Master：“我需要订阅 `/target_pose` 话题，请问谁有？”
3. **第 3 步：Master“牵线搭桥”**。 Master 查阅注册表，发现匹配上了。于是它回复控制节点：“YOLO 视觉节点在发布这个话题，它的地址和端口是 IP:4321，你自己去找它吧。” （到此为止，Master 的任务就结束了）。
4. **第 4 步：节点间“私下协商”与建立连接**。 控制节点主动向 YOLO 视觉节点的 4321 端口发起请求，双方确认使用 **`TCPROS`** 协议传输数据。随后，一条专门的 TCP 连接在两个节点之间建立。
5. **第 5 步：数据发布与流转**。 当 YOLO 模型输出了新一帧的目标位姿，ROS 1 会将这个 C++ 对象**序列化**成字节流，通过刚才建立的 TCP 管道发送过去。控制节点收到字节流后，再**反序列化**还原成代码可以读取的位姿对象。

对于ROS 2，没有了 `roscore`，发布这个位姿话题的过程变成了完全的点对点（P2P）广播与匹配：

1.  **第 1 步：底层 Participant 的“组播宣告”** YOLO 视觉节点和机械臂控制节点在启动的瞬间，底层的 DDS 就各自创建了一个“参与者（Participant）”。它们会立刻向局域网特定的 UDP 组播地址大喊：“我上线了！”。互相收到宣告后，双方知道了彼此在同一个网络里（发现阶段一：PDP）。
2. **第 2 步：端点（Endpoint）细节交换与 QoS 匹配** 建立联系后，YOLO 视觉节点（`DataWriter`）告诉控制节点：“我会发布 `/target_pose` 话题，我的 QoS 策略是 `Reliable`（必须可靠送达）。” 控制节点（`DataReader`）回应：“我正好要订阅 `/target_pose`，我的 QoS 也是 `Reliable`。” **注意：** 如果此时你的视觉节点为了追求极低延迟，把 QoS 设为了 `Best Effort`（尽力而为），而控制节点要求 `Reliable`，它们虽然认识，但**话题将无法连通**。只有 QoS 兼容，底层的传输通道才会真正打通（发现阶段二：EDP）。
3. **第 3 步：数据发布** YOLO 检测到目标，调用 `publish()` 函数。底层的 DDS 会接管这个位姿数据，根据之前协商的 QoS 策略（比如如果是同机运行，DDS 可能会智能地使用共享内存机制），直接将数据高效地投递给控制节点的内存中，省去了繁琐的 TCP 握手和无谓的网络层开销。
