# 调试方法与机器人项目实战

> 调试的核心是：把异常变成可重复的实验，用证据找到最早出错的位置，再证明修复有效。

本文面向知识库中的 C++、ROS2、机械臂与运动规划学习。案例是教学示例，不代表我们已经完成的项目排障经历。先读第 1～3 节，再动手完成第 5 节，随后按项目选择专项练习。

## 1. 先建立一套固定流程

遇到问题时，按这六步推进：

1. **描述差异**：什么输入、期望什么、实际什么。把“机械臂不动”改成“轨迹请求已接受，但 5 秒内关节反馈未变化”。
2. **固定现场**：保存版本、启动命令、参数、输入和完整错误日志。随机算法保存种子；多线程问题还要记录负载与运行次数。
3. **最小复现**：减少节点、数据量和依赖，直到保留问题的最小程序或场景。
4. **提出可验证假设**：每个假设写明“若成立，应看到什么；如何否定”。一次只改变一个关键条件。
5. **定位并修复原因**：找到最早违反接口约定或数据不变量的位置，解释它如何导致最终现象。
6. **做回归并复盘**：原失败输入通过、邻近边界通过、正常输入不退化；留下可复现记录。

**现象、假设、证据、结论要分开写。** “加了延时就好了”是现象；只有证明初始化顺序有问题，才有资格把原因写成初始化竞态。

### 卡住时的三个问题

- 哪个环节的输入已被证明正确，哪个环节的输出首次错误？
- 下一次实验能排除哪一个假设？如果不能排除，先别改代码。
- 能否用固定输入替代上游，或绕过一半模块，缩小范围？绕过仅用于定位，不能当最终修复。

## 2. 按故障阶段选择工具

| 现象 | 优先检查 | 第一份有用证据 |
|---|---|---|
| CMake 配置失败 | 编译器、生成器、依赖路径、配置日志 | 首个具体失败步骤及完整错误 |
| 编译失败 | 类型、声明、头文件、模板实例化上下文 | 第一处相关编译错误 |
| 链接失败 | 实现是否参与构建、库依赖、符号与 ABI | 缺失或重复符号、链接命令 |
| 启动失败 | 配置路径、动态库、插件、运行环境 | 实际启动命令与加载错误 |
| 崩溃或异常退出 | 调用栈、对象寿命、越界、异常 | 调试器堆栈或内存检测报告 |
| 输出错误但不崩溃 | 输入契约、单位、索引、边界、坐标系 | 第一个异常中间量 |
| 卡住或偶发失败 | 锁、等待条件、线程、回调调度 | 所有线程堆栈和事件时间线 |
| 运行慢 | 各阶段耗时、输入规模、负载 | 相同条件下的耗时分布 |
| ROS2 收不到消息 | 节点、话题、类型、QoS、发现范围 | 发布订阅端点信息 |

“最后一行报错”常是汇总结果；从上下文中找第一个有解释力的错误。崩溃行也可能只是较早内存破坏的受害者。

## 3. 最低限度的证据与日志

每次排障先记录以下内容，不必一开始就写长报告：

```text
问题：
代码版本 / 未提交改动：
系统 / 编译器 / 构建类型 / ROS 发行版：
工作目录 / 启动命令 / 参数文件：
输入数据 / 随机种子：
期望结果 / 实际结果：
复现次数：失败 __ 次 / 总共 __ 次
最早异常日志及其前后文：
```

日志要能还原因果链。机器人项目可优先记录 `request_id`、节点名、事件名、时间戳、坐标系、数据尺寸、关键数值和错误原因。例如：

```text
request_id=42 event=trajectory_rejected reason=joint_count_mismatch expected=6 actual=5
```

- 测量耗时使用单调时钟；比对 ROS 消息时明确使用系统时间还是仿真时间。
- 高频控制循环中避免每周期同步打印大量文本，可用计数、节流或缓冲记录。
- 日志可能改变线程时序；“打开日志不再复现”不能证明修好了。
- `assert` 适合表达内部不变量，但发布构建可能禁用断言。外部输入校验和必要的运行保护应使用明确的错误处理。

## 4. 先确保调试的是正确程序

### 构建配置

以下命令在实际 CMake 项目根目录运行，要求编译器和 CMake 已安装。`build-debug` 应为本次新建或已确认配置一致的目录。

单配置生成器（如普通 Ninja、Unix Makefiles）：

```sh
cmake -S . -B build-debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build-debug --verbose
```

Visual Studio 等多配置生成器：

```powershell
cmake -S . -B build-debug
cmake --build build-debug --config Debug --verbose
```

`CMAKE_BUILD_TYPE` 用于单配置生成器；多配置生成器在构建时选择配置。更换编译器或生成器时使用另一个构建目录，保留旧日志以便比较。[CMake 官方说明](https://cmake.org/cmake/help/latest/variable/CMAKE_BUILD_TYPE.html)

如果断点不生效或改代码没有变化，先确认：运行文件的完整路径、构建是否成功、调试符号是否匹配、当前源码是否对应这个文件。ROS2 还需确认终端加载的是目标工作空间。

Debug 构建便于观察变量；只在 Release 出现的问题仍应在接近原优化条件、带符号的构建中复现。改变优化级别可能掩盖未定义行为或时序问题。

### 调试器最常用操作

| 目的 | GDB | Visual Studio 对应操作 |
|---|---|---|
| 在目标函数暂停 | `break function_name` | 函数断点或行断点 |
| 开始 / 继续 | `run` / `continue` | 开始调试 / 继续 |
| 执行下一行 / 进入函数 | `next` / `step` | 逐过程 / 逐语句 |
| 查看变量 | `print variable` | 监视 / 局部变量 |
| 查看调用链 | `bt`、`frame 1` | 调用堆栈，切换栈帧 |
| 查看所有线程堆栈 | `thread apply all bt` | 线程 / 并行堆栈窗口 |
| 在变量变化时停下 | `watch variable` | 数据断点（支持情况依目标而定） |

调用栈回答“怎么走到这里”；观察点回答“谁改坏了它”。观察点应在变量可访问且对象仍存活时设置，硬件资源和平台支持有限。[GDB 调用栈](https://www.sourceware.org/gdb/current/onlinedocs/gdb.html/Backtrace.html)、[观察点](https://www.sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Watchpoints.html)

## 5. 第一个完整练习：C++ 越界

把下面代码保存为独立练习目录中的 `debug_demo.cpp`。它故意包含错误，只用于练习。

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> values{10, 20, 30};
    int sum = 0;
    for (std::size_t i = 0; i <= values.size(); ++i) {
        sum += values[i];
    }
    std::cout << sum << '\n';
}
```

### 先取证，再改动

1. 写下期望：输出 `60`。
2. 用调试器在循环体设置条件断点 `i == values.size()`，观察 `i` 与有效索引范围。
3. 如果在 Linux/WSL 中已安装 Clang 及 sanitizer 运行库，可运行：

```sh
clang++ -std=c++17 -g -O1 -fno-omit-frame-pointer -fsanitize=address,undefined debug_demo.cpp -o debug_demo
./debug_demo
```

4. 查看报告中的访问类型、源代码位置以及分配信息。本例预期被检测为越界读取；具体文本随工具链变化。
5. 将循环条件改为 `i < values.size()`，用相同命令重新编译运行。
6. 分别测试空容器、单元素 `{10}`、原输入，预期为 `0`、`10`、`60`。

根因是把容器长度当成了最后一个有效下标。即使原程序偶尔输出 `60`，越界访问仍是未定义行为。

AddressSanitizer 用于检测越界、释放后使用等内存错误；需要在构建及最终链接时启用相应选项。一次运行没有报告，只能说明该次执行没有检测到对应问题。[Clang AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html)

Windows 原生 Visual Studio 用户可用断点完成相同练习；上面的 Clang 命令面向 Linux/WSL，不是 MSVC 命令。

## 6. 并发与性能问题

### 卡住时

先暂停程序并收集所有线程堆栈，再区分：锁等待、阻塞 I/O、忙循环、条件变量等待，还是回调根本未获得执行机会。

例如，一个线程持有锁 A 等 B，另一个持有 B 等 A，才构成可解释的锁等待环。单个线程停在加锁函数，不能独自证明死锁。

ROS2 中还应检查：回调是否同步等待一个依赖同一执行器或互斥回调组才能完成的任务。盲目增加线程数不一定解除这种等待。

### 怀疑数据竞争时

记录共享变量的读写者和同步方式。Linux/WSL 下可另建检测版本，编译和链接启用 `-fsanitize=thread -g -O1`。ThreadSanitizer 检测数据竞争，应与 AddressSanitizer 分开构建和运行；它不能证明所有并发逻辑正确，也不能替代死锁分析。[Clang ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html)

`volatile` 不提供线程间互斥；加 `sleep` 不建立正确的同步关系。修复应围绕明确的所有权、锁、原子操作或任务调度规则。

### 运行慢时

先拆分输入读取、预处理、推理、碰撞检测、搜索、平滑、通信等阶段，再优化最贵的部分。比较时固定硬件、输入规模、构建类型、预热和计时边界。

至少记录样本数、失败率、中位数和 P95；对规划超时说明如何统计。仅比较成功样本平均值可能把更容易超时的版本误判为更快。检测器会增加开销，性能基准应使用独立的正常构建。

## 7. ROS2：话题存在，但订阅没有数据

以下是 ROS2 CLI 排查示例。先加载已安装发行版及项目工作空间的环境；将话题名和节点名替换为实际值。选项以本机 `--help` 为准，不与 ROS1 命令混用。

```sh
ros2 node list
ros2 node info /controller
ros2 topic list -t
ros2 topic info /joint_states --verbose
ros2 topic echo /joint_states
ros2 topic hz /joint_states
```

依次确认节点存在、端点对应、类型一致和 QoS 信息。`topic info --verbose` 可查看发布订阅节点与 QoS 配置。[ROS2 话题教程](https://docs.ros.org/en/lyrical/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Understanding-ROS2-Topics.html)

排查顺序：

1. **节点与发现**：进程是否启动？多机是否在预期网络与 ROS domain 内？
2. **名称与类型**：命名空间或 remap 是否改变了实际话题？消息类型是否一致？
3. **QoS**：发布者提供的策略与订阅者请求的策略是否兼容？
4. **真实发布行为**：发布循环是否运行？是否被条件分支跳过？
5. **订阅处理**：回调是否进入，是否阻塞，是否收到后因时间戳或数据校验而丢弃？

教学案例：端点可见，发布者使用 best effort，订阅者要求 reliable。这一 reliability 组合不兼容。将订阅需求调整为项目允许的策略后重新验证；还需检查 durability 等其他策略，不能只看 reliability。[ROS2 QoS 兼容规则](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Quality-of-Service-Settings.html)

CLI 本身也是订阅者，其 QoS 与处理能力会影响观测。`echo` 能收到不代表目标节点配置正确；`hz` 是观测端的接收频率，不能直接当作发布端的精确频率。

## 8. 机器人专项：数值看着合理，结果却错

### 坐标变换与视觉定位

先给每个量写清单位、坐标系和时间戳，再检查矩阵乘法。定义 `T_A_B` 为“将 B 系坐标转换到 A 系”：

```text
p_A = T_A_B · p_B
T_A_C = T_A_B · T_B_C
```

不要只写含义不明的 `T_cam`。按下表建立最小实验：

| 检查项 | 最小验证 | 可发现的问题 |
|---|---|---|
| 单位 | 输入已知 0.1 m 平移，核对输出 | 米 / 毫米混用 |
| 角度 | 输入已知 90° 旋转，并明确转为弧度 | 度 / 弧度混用 |
| 方向 | 用原点和三个基向量验证变换 | 正逆变换、乘法顺序错误 |
| 旋转有效性 | 检查 `RᵀR ≈ I`、`det(R) ≈ 1` | 非法旋转；但无法证明标定正确 |
| 四元数 | 核对接口是 xyzw 还是 wxyz、是否归一化 | 分量顺序或尺度错误 |
| 时间 | 静止正常、运动异常时比对采样时刻 | 图像与关节状态不同步 |
| 深度 | 已知距离物体，核对尺度及无效值 | 深度单位、对齐或无效像素问题 |

教学案例：目标在相机前方 0.5 m，转换后落在基座后方。先用恒等变换与已知平移替换标定结果，再单独验证相机到末端、末端到基座两段，检查是否取反或重复应用变换。

### 规划失败或轨迹穿障碍

按“输入有效性 → 碰撞模型 → 搜索过程 → 路径后处理 → 执行接口”排查：

- 起点、终点是否越界或碰撞？逆解是否存在？
- URDF、关节顺序、碰撞几何与实际场景是否一致？
- 规划器是否超时，采样和扩展是否实际进行？
- 节点无碰撞，节点之间的运动是否也经过足够的碰撞检查？
- 平滑、插值之后是否重新检查路径有效性？
- 轨迹关节名称、位置数组顺序和控制器约定是否一致？

固定场景与种子，将自定义规划器和基线放在相同预算下比较。一个种子复现问题用于定位，多个种子与场景用于检验修复。不要直接把增加超时时间当作根因修复。

### 规划成功但机械臂不动

分别取得四段证据：规划返回结果、轨迹发送及接受结果、控制器执行反馈、真实关节状态变化。按请求编号和时间关联它们，找到链路在哪一段中断。

涉及真实机械臂时，暂停和单步会改变控制时序；故障注入、断点与不可靠轨迹先在离线或仿真环境验证，再依项目流程进行受控实机验证。

## 9. 最容易浪费时间的习惯

| 习惯 | 为什么低效 | 替代做法 |
|---|---|---|
| 一次改很多参数 | 无法判断哪个改动有效 | 每轮记录单一变量及结果 |
| 反复重启直到成功 | 丢失偶发问题证据 | 记录成功与失败条件差异 |
| 直接吞掉异常 | 表面继续运行，内部状态可能已错 | 保存上下文并明确处理失败 |
| 先重装所有依赖 | 改变现场且难以回退比较 | 先检查实际加载路径与版本 |
| 加 sleep 修并发 | 时序换了，原因可能还在 | 建立可解释的同步机制 |
| 只凭 RViz 画面判断 | 显示正常不保证数值或时间正确 | 同时核对原始消息和计算结果 |
| 让 AI 连续猜原因并改代码 | 假设未经验证会不断扩大改动 | 提供最小复现，要求验证步骤 |

## 10. 七次动手训练

每次建议 45～90 分钟。结束时至少交付一份日志、一条根因解释和一个回归用例；尚未定位也要写下已排除的假设。

| 次序 | 任务 | 验收标准 |
|---|---|---|
| 1 | 完成第 5 节越界练习 | 找到错误索引，三个输入通过 |
| 2 | 在小项目中故意让一个实现文件不参与构建 | 区分编译与链接错误，解释缺失符号 |
| 3 | 练习断点、条件断点、调用栈、观察点 | 找到变量首次被错误修改的位置 |
| 4 | 在纯软件 ROS2 发布订阅示例中制造 QoS 不兼容 | 保存端点证据，恢复通信并解释原因 |
| 5 | 为坐标变换构造恒等、平移、旋转用例 | 预先手算期望值，明确方向与单位 |
| 6 | 在仿真规划中设计无障碍、窄通道、非法目标场景 | 对失败分类，而非只写“规划失败” |
| 7 | 复做一项练习，由同伴选择故障位置且不提前告知 | 独立复现、定位、修复并完成复盘 |

不会编写完整项目时，先用独立 C++ 小程序练方法，再移入现有机械臂模块。阅读文档只算准备，完成可复现案例才开始形成经验。

## 11. 可复制的调试复盘模板

```markdown
### YYYY-MM-DD｜问题标题

- 环境与版本：
- 期望 / 实际：
- 复现步骤及输入：
- 失败次数 / 总次数：
- 首次异常位置与证据路径：
- 假设 A、验证方法、观测结果：
- 假设 B、验证方法、观测结果：
- 根因与因果链（未确认则明确标注）：
- 修复内容及为什么有效：
- 回归：原失败用例、边界用例、正常用例：
- 剩余限制与后续动作：
- 下次如何更早发现：
```

讲项目经验时，可以用“现象 → 假设 → 实验 → 根因 → 修复 → 回归”组织回答。未经实际运行的练习不能写成已完成的排障经历。
